# 项目愿景 / 维护方向

> 本文档是本仓库维护的**单一权威基线**（Direction / Decision Record）。
> 一切改动、重构、新建模块，**先与本文档对齐**，再进入 `docs/` 下各自的 TODO / 契约文档。
> 当其他文档与本文档冲突时，以本文档为准，并把冲突处改回与之一致，避免反复返工。

## 1. 项目定位

- 用途：**私有自用**（作者本人 + 少数朋友），**无对外发布需求**。
- 因此：部署/构建负担很小，"npm install + build + 本地起服"完全可接受，不构成迁移障碍。
- 内容：多款游戏（GI / SR 等）的**数据浏览型静态站点**。

## 2. 资产边界（不可破坏 vs 可自由重设计）

这是整个方向的基石 —— 分清"什么绝不能动"和"什么随时可重来"：

| 层 | 归属 | 处置规则 |
|----|------|---------|
| **数据 JSON**（`gi/**`、`sr/**`、`/sr/data/**` 等） | 原作者核心资产 | **只读即加不改**，结构基本冻结 |
| **视觉样式（CSS）**（`stylesheets/**` 及页面内 `<link>`） | 原作者核心资产，也是**最宝贵的部分** | **不动主体**，仅按需微调 |
| **JS 页面内容**（`javascripts/**`、页面引用的脚本） | 原作者核心资产（其一），但可渐进改进 | 是**渐进改造**的对象，不许推倒重来 |
| **构建 / 部署骨架**（`server.py`、`server.bat`、`update.ps1`、`update.bat` 等） | **非原作，作者本人为"先跑起来"临时自建** | **随时可重设计 / 重建 / 替换**，无历史包袱 |
| **数据转换脚本**（`test_monster_update.py`、`hsr_*.py` 等） | 非原作，自建 | 可**换其他形式更新数据**，可重写 |

> 结论：**真正不可破坏的是「数据 + 文件样式」这两样**。骨架与数据管线是作者自己的选择，绝不反过来限制这套资产能走多远。

## 3. 数据与展示

- 展示 =「取 JSON → 排版 → 交互」，基本是**数据驱动的列表/详情型**。
- 视觉尽可能集中在 **CSS**，JS 只负责"产出符合现有 class/结构 的 DOM"。
- 因此**视觉样式与 JS 实现是解耦的**：迁移/重构时只要**沿用旧 DOM 结构 + class**，CSS 自然复现，视觉即可复原。

## 4. 技术方向：短期 A（渐进，不全面重构）

**当前决定：采用方向 A —— 保留静态站点形态，渐进改造，短期不做全站/全页重构。**

选 A 的理由（记录在案）：
- 全面重构工作量太大（几百个页面），且存在"视觉可否复原"的未知风险，性价比低。
- 项目为自用，没有必须"追上现代架构"的外部压力。
- 最宝贵的数据与样式，用"渐进 + 保留 DOM/class"的方式最稳妥。

A 的具体约束：
- **不推翻现有页面**；只在真正动到的页面做渐进修改。
- 渲染层以**标准化、可复原**为准则，禁止随手改 DOM 结构或 class。
- 以 **ach（GI / SR 成就页）为试点**，验证"渐进改造且视觉可复原"的可行性与工作量，再决定是否推广。

## 5. 长期演进（可选，不承诺）

- 未来若确需更现代架构（如 Vue/TS），**前提是不破坏第 2 节的数据与样式**。
- 届时依然是"以数据为源、CSS 保留、重写 JS 实现层 + 对齐 class"，而不是推倒重来。
- 是否演进，由"改造收益 vs 复原风险"决定，不被"想用新框架"这个单一动机推动。

## 6. 文档结构约定

- `docs/renderer-contract.md`：渲染层契约（**待建立**），规定 DOM/class/转义/加载等，落实"视觉可复原"。
